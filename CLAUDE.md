# Gridiron Drive (Football)

A browser American-football game in plain JavaScript ES modules: `index.html` loads three.js r128 from cdnjs and `src/main.js`; physics in `src/physics.js` (cannon-es style rigid parts). No build step, no package.json.

Team process: a project-manager (PM) leads; workers build on their own branches and worktrees (`../football-wN`); the PM moves main. Backlog: `docs/BACKLOG.md` (shape in its header). Process rules: `~/.claude/pm-board/ROLES.md`.

## Run and serve

- Serve: `npx vite --host 127.0.0.1 --port <port> --strictPort` from the repo root (plain index.html; no config needed). To stop it later, launch it in the background with a pidfile at a literal scratchpad path: `npx vite --host 127.0.0.1 --port <port> --strictPort > <scratch>/vite.log 2>&1 & echo $! > <scratch>/vite.pid`. Stop it with `kill $(cat <scratch>/vite.pid)` in a Bash call of its own (policy takes a literal PID or that form, never `kill $VAR`). `$!` is npx's wrapper: then run `lsof -nP -iTCP:<port> -sTCP:LISTEN -t || true`; no output means nothing listens (lsof alone exits 1 then: not a failure), and a PID it prints is your vite's child only if `<scratch>/vite.log` shows yours started (a line with `Local:` and `http://127.0.0.1:<port>/`, no `Port <port> is already in use`): then kill that literal PID too; otherwise the listener is another session's: leave it and tell your lead. sim-pool `--tree` and visual-shots stop their own servers: no check after them unless they print `still alive` (then the leftover is in their own process group and yours to stop per the stop-process skill). Steps: the stop-process skill. A main copy (for a before/after; it is your branch's base, so other merges since you started never show as your change): `rm -rf <scratch>/base && mkdir -p <scratch>/base && git -C <your worktree> archive $(git -C <your worktree> merge-base main HEAD) | tar -x -C <scratch>/base`, made again after a rebase or a merge from main (then rerun main's pool or shots too), served by absolute path, never cd into it: the same command with `<scratch>/base` added after `--strictPort`. A fix round reruns the branch only (user L-1008-070: fix rounds were slow): main's pool and main's shots in your scratchpad stand while the base holds and the seeds, N, params and shot queries are the same (the shot file or projects.json `visualShots` unchanged since main's run, else rerun the changed shots on main). A frame added or a play set not run before runs on main for those shots only. A new session has no main results: it runs main again. The branch's pool is rerun whole, never `--keep` across rounds (a new commit is a new build).
- Open http://127.0.0.1:<port>/.

## Checks

- Fast check: `for f in src/*.js; do node --check "$f" || exit 1; done` (syntax only).
- Full check: the fast check, then load the page in headless Chrome (the agents' browser is off for now, user L-1006-070). Serve as in Run and serve (with the pidfile; stop it after); `<scratch>` is your session scratchpad (an existing directory). Then:
  `~/.claude/pm-board/headless-dump.sh http://127.0.0.1:<port>/ <scratch>/run 40` (args: URL, output prefix, alarm seconds). It writes `<scratch>/run.dom` (the DOM dump) and `<scratch>/run.err` (Chrome's log), stops Chrome once the dump is whole (Chrome otherwise lingers until the alarm), and removes its throwaway profile on exit or a signal (P-436: leftover profiles filled the disk on 2026-10-07). Use this wrapper, never a copied Chrome line or a script of your own around it; for a long run, run the call with run_in_background. Exit 0: dump whole; 142: the alarm came first.
  Pass: `grep ':CONSOLE' <scratch>/run.err | grep -vE '\[vite\]|GPU stall'` prints nothing, and `grep -c '<canvas' <scratch>/run.dom` is 1 or more. Every console message (console.error and warn too) is logged as an INFO CONSOLE line, so any line but the vite and WebGL "GPU stall" noise is a failure. A module that fails to load (a 404, cdnjs unreachable) logs nothing; the missing `<canvas` catches it. A fresh profile per run (the wrapper makes one each time) matters: a reused one can serve cached modules from an earlier build (e.g. another worktree's server on the same port), with no console sign. Whether a play runs (snap, pass or run, play ends) is the user's look at a play in the browser: say in the done-report what to look at.
- Sim check: serve and run the headless recipe with `?sim=100&seed=7` as the URL (the dump is written when the sim finishes: about 35-40 s for N=100 under swiftshader, longer on a busy machine, so pass 90 in place of 40 as the alarm here, and more if N is larger (roughly 0.4 s a play, so N=300 wants alarm 180 or more); an empty run.dom (exit 142) means the alarm came first). Pass: `grep -o '<pre id="simout">[^<]*' <scratch>/run.dom` prints one JSON line; every field, and the force, awareness and personnel params, is listed in the header comment of `src/sim.js` (the sim.js owner keeps it current; B-023); the same seed gives the same line; pile counters count tackle/ragdoll bodies only (`p.ph && !p.ph.bubble`) and bodiesMax is the total physics body count. Optional force params `&play=<run play>&front=<defensive call>&form=&side=L|R` (names case-insensitive; an unknown or pass play gives {"error":...}; form and side are echoed only until B-007-3/4). Awareness: `&olrecog=N` sets every OL and TE recog to N (re-applied after each team regen). Personnel: `&pers=11|12|21|22` and `&dpers=nickel|base|odd` (aliases 4-2-5, 4-3-4, 3-4-4; also work on a normal page load; unknown gives {"error":...}); the line then adds force.pers/dpers, field {off, def} (position counts on the last play) and roster {O, D, ids unique, on}. physMs median/p95 are not reliable here: usually null (performance.now doesn't advance within one synchronous task), sometimes a number depending on timing, so never compare them; use `?debug` in a real browser for frame and physics ms. `?sim` seeds Math.random for the whole page; a normal load is unchanged.
- Frames check (render-side changes; headless Chrome runs only about 3 animation frames, so this steps the render synchronously): serve and run the headless recipe with `?drill=1v1|line&frames=N&sim=1&seed=S` as the URL (N=3600 wants alarm 150). Pass: `grep -o '<pre id="checkout">[^<]*' <scratch>/run.dom` prints one JSON line (the engaged-pair overlap fields, listed in the header comment of `src/animation.js` pairReport: anyPct, padsInBodyPct, headHeadPct, headInBodyPct, armInBodyPct, armArmPct, medDsim, medDrender); the same seed gives the same line; `?frames` without `?drill` gives {"error":...}; the full check's pass (no console lines but the noise, `<canvas` 1 or more) applies too, so a missing `<pre>` from a module that failed to load is not read as a failing frames line. With B-037, `&play=<run play>` picks the drill play (default Iso) and the line adds second-man double-team fields (dblAnyPct, dblPadsPct, dblHeadPct, dblFrames, dblJumpMax under 0.09, dblOffsetJumpMax, dbl1v1JumpMax control, dblFades, dblJumpKind; listed in pairReport); B-037 baseline IZ vs 4-3 Over seed 7 dblAnyPct 18.5, Duo vs 4-3 Under seed 11 21.4. At B-042 (main 166f583, line seed 7): anyPct 17.4, padsInBodyPct 3.3, headHeadPct 3.5; headOffNeckMax and limbStretchMax 0 (head on its neck socket; each joint vs its socket, physics bodies included; stretchAt names the worst); IZ dblAnyPct 12.3, dblJumpMax 0.1. `&cam=side` gives a side-on drill camera; `?frames` paints the last frame for a screenshot. `&handoff=N` forces an engaged man into a physics body every N frames: handoffMax (drawn jump at the hand-off, yd) under 0.08. - Visual check (P-443, user L-1007-120/121: numeric checks passed while heads sat beside torsos). A change to src/animation.js, src/scene.js, src/camera.js, src/markers.js, src/hud.js, src/drill.js, src/physics.js, src/tackling.js or index.html is looked at before review. One build after the other, on the port in your brief only (another port is another worker's), with one command per build (P-447): copy your base as in Serve (the main copy), then `node ~/.claude/pm-board/visual-shots.mjs <scratch>/base --project football --port <port> --build main --out <scratch>/shots` and the same with `<your worktree> ... --build branch`. It serves that tree, takes every shot in projects.json `visualShots` into `<scratch>/shots/<build>-<shot>.png`, and stops its own server; exit 2 on a busy port means another server is up there (never stop it), 1 a shot failed. The shots, per build (the list itself: `node ~/.claude/pm-board/projects.mjs football visualShots`): the drill from behind and from the side at frames=600 and again at frames=40 (pre-snap stance: the linemen set, not the opening frame), frames=40 `&cam=los` (low profile, both lines set, the center's hand on the ball), a normal load (the game camera's pre-snap view), and in play via `?autoplay=1.5` and `3` (B-046; the 3 s play may already be whistled, banner up); all seeded 7 but the normal load. A new shot is a request to the analyst (projects.json). A change to play footwork, blocking or run fits (a cut, a pull, a shed, DB or LB steps, a DL's fit or chase) also runs the optional set, both builds: `--shots ~/.claude/pm-board/shots/football-play.json --build main-play` (and `branch-play`): a forced pass play from the side, a forced run close, and the first cut, pull and shed close (B-081, B-086; `&stopon=<ev>&after=<n>`; the cut 9 steps in, mid-plant, after the brake). Open each PNG with Read and compare main with the branch. Fail: main and branch shots that look the same on a change meant to show (the shot missed it: add a frame where it shows, both builds, with `--shots <file.json>` holding only the added frame(s) as `[{"name", "query", "alarm"}]` (it replaces the list for that run), and say which), a blank or frame-0 picture, bodies through each other, a head or limb off the body, a pose the task didn't ask for. In play (B-046, `?autoplay=<s>&sim=1&seed=7`): the CPU calls and snaps, the sim steps synchronously and stops s seconds after the snap or at the whistle; `<pre id="autoout">` holds {autoplay, stoppedAt, phase, steps, digest}, and the same seed gives the same line (compare the digest) and the same-looking picture (the PNG bytes can differ; without sim=1 it is unseeded). A normal load is unseeded, so rosters and ratings may differ between the two pre-snap game shots: compare bodies and poses only. The done-report's Verification carries `Visual: <the 8 shots per build, main and branch (16 pngs), plus the 5 play shots per build when the play set runs, plus any frame added>; seen: <one line per camera>`; the branch-reviewer reads them.
- Reading the JSON lines (P-445): `node ~/.claude/pm-board/headless-json.mjs <scratch>/run.dom simout` prints the Sim check line (also `checkout`, `autoout`); `--diff <scratch>/base.dom` compares two runs field by field (one `path: a -> b` line each, `equal` when none; exit 1 on a difference) and `--zero physMs` leaves out fields that aren't reliable headless. Exit 2 means the line is missing, not JSON or an `{"error":...}` (a bad param): the run failed, never a pass. Use it instead of a script of your own.
- Pooled sim (P-446, user L-1008-001; physics changes, or any change the Sim check numbers judge): one seed says nothing, since a physics change makes each seed's run diverge. Main first, then the branch, one after the other on the port in your brief; sim-pool serves each tree itself and stops its server (P-449, user L-1008-021; a busy port exits 2, never stop another session's server). Copy your base as in Serve (the main copy), then `node ~/.claude/pm-board/sim-pool.mjs --tree <scratch>/base --port <port> --project football --out <scratch>/pool-main`, then for the branch `--tree <your worktree> --port <port> --project football --out <scratch>/pool-branch --vs <scratch>/pool-main` (seeds 7-11, N 200 a seed, about 80 s each; `--n`, `--seeds` and `--params '&play=<run play>'` override, the same for both builds). Exit 3 "branch matches main" (P-448, user L-1008-007): the branch's first seed equals main's, so the edit did not take or does not reach the sim; find out why before pooling again. A pool whose `--params` never reach the changed code runs without `--vs` only when you can name why (a forced play that skips a rare path), and the done-report says so: the early stop is only for pools that should differ (worker-3, B-074). A change meant to leave the Sim check line as it is (a readout or tooling change) pools without `--vs` from the start and must match exactly, seed by seed: `headless-json.mjs <scratch>/pool-main/seed<S>.dom simout --zero physMs --diff <scratch>/pool-branch/seed<S>.dom` prints `equal` for every seed, or only `<field>: (missing) -> <value>` lines for fields it adds; the pooled FLAG count is not the pass, since a stray RNG draw keeps the means within 2 sd (worker-1, B-088; report it as `no --vs (meant equal)`). Exit 2 before any run: main's first seed is missing or bad (run main first, with the same `--seeds`). Then `node ~/.claude/pm-board/headless-json.mjs --pool <scratch>/pool-main simout --zero physMs --diff <scratch>/pool-branch`: each FLAG line is a field present in every seed that moved more than 2 seed-sd, which is a real change to explain in the done-report (fields in only some seeds are counted, not judged; if that count moves much between builds, read `--partial`). A failed seed (sim-pool exit 1, headless-json exit 2) is rerun, never read as a pass: the same command with `--seeds <the failed ones> --keep` (P-450, user L-1008-025) replaces only those and keeps the good seeds; same build and params only, else rerun the whole pool. The done-report's Verification carries `Pooled sim: <seeds, N, params; --vs, or no --vs (<why>); FLAG fields or none; the diff file> | skipped (<why>, which the reviewer judges)` on any change this bullet covers (worker-2, a skipped pool showed nowhere in the report).

## Design rules

To be written by the PM with the user (design-talk). Until then: keep modules small and single-purpose, no globals beyond `state.js`'s `S`, tunables as named constants at the top of their module.
- Physics engine calls (cannon-es: bodies, constraints, world, impulses) stay inside src/physics.js, src/tackling.js and src/pile.js; other modules use only their exported functions (physBall, physDown, physTouched, ...) and the `p.ph` handle as an opaque flag, so a later Rapier swap stays one contained job (user L-1006-146).
